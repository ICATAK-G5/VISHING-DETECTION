# Flutter phone client

The Flutter app provides QR scanning, manual pairing details, desktop approval status, secure connection status, retry, and forgetting a desktop. Phase 3 keeps Cellular Protection as an opt-in Android foreground-service mode, and adds a separate user-started controlled WebRTC audio session plus asynchronous voice messages. The controlled modes are not cellular-call capture and do not claim access to SIM-call audio.

The Android wrapper is included. From this folder, run `flutter pub get`, then `flutter run` with an Android device selected. The app needs camera access for QR scanning and internet access for the desktop connection.

In **Controlled Digital Audio**, a paired phone can start a direct WebRTC microphone stream to the Python desktop peer. For a controlled Phone A ↔ Phone B call, both phones must be paired and connected to the same desktop. The app shows every other paired phone in a visible device list; tap its call icon to call, or its end-call icon to disconnect. Phone B receives an explicit accept/decline prompt. The desktop issues the call ID and fixes Phone A as `far` (caller) and Phone B as `near` (receiving/protected phone), so users do not select audio roles. SDP and ICE signaling use the authenticated control socket; call audio travels peer-to-peer over WebRTC. Only Phone B forwards audio to the dashboard: its local microphone as `near` and the decoded Phone A track as `far`. The dashboard groups the two streams under the desktop-issued call ID. In-app calls use the phone earpiece by default to reduce speaker-to-microphone acoustic feedback; speakerphone capture is not guaranteed. Starting an outgoing controlled app call stops Cellular Protection on that caller phone so it does not create a second capture session. Android's generic cellular `CALL_STATE_OFFHOOK` still cannot distinguish an outgoing cellular call from an incoming or active one. Same-Wi-Fi testing uses host ICE candidates; cross-network STUN/TURN is not configured. This in-app call is not a cellular call and does not capture SIM-call audio.

In **Voice message**, the user explicitly records a clip. Outside a call it can be sent directly to the desktop over the pinned HTTPS connection. During an app call either participant can offer the clip over an ordered, encrypted WebRTC data channel; the recipient must accept, and the transfer is capped at 25 MB and checked against SHA-256 before the received file is made available. The recipient can then send it to the desktop. The desktop decodes and stores normalized WAV for up to 24 hours; the loopback dashboard can play or immediately delete each clip. The service does not yet run batch analysis; that belongs to later analysis phases.

Flutter resolves `flutter_webrtc`, `record`, and `path_provider` from `pubspec.yaml`. Android permissions include network-state/audio routing support; the app requests microphone access only after the user starts a controlled audio mode. The Android target minimum is 23 for the selected WebRTC plugin. Current same-LAN media relies on local ICE candidates; the app and desktop service must both be connected to the same trusted private network, and the Windows Python service may need a Private-profile firewall allowance for its UDP media sockets.

The existing **Send diagnostic tone to desktop** path remains a WebSocket transport check. It does not read the microphone or capture call audio. The dashboard’s 60-second RAM preview can play its samples. `scripts/replay_audio.py` separately replays a local file as paced 20 ms VDA1 frames at 50 frames per second for WebSocket diagnostics.

To connect a physical phone, connect it and the desktop to the same trusted Wi-Fi. In the desktop dashboard, enable **Allow paired phones on local network**, stop the desktop service in its terminal (Ctrl+C), and start it again with `scripts/start_desktop.ps1`. Wait until the dashboard says **LAN enabled**. Choose the desktop's address on that Wi-Fi, then click **Start pairing** and scan that newly generated QR code. Do not reuse a QR generated before the service restart; it may point to `127.0.0.1`, which refers to the phone itself. After a successful scan, the dashboard displays the phone request for approval.

If using manual pairing, copy the **Phone address**, **Fallback code**, and **TLS fingerprint** from the desktop dashboard. The mobile form describes each source. The phone address must be the desktop's Wi-Fi IPv4 address, not `127.0.0.1`.

If pairing reports a timeout, check whether the desktop dashboard has a pending phone request. A pending request means the QR request reached the service; approve it and keep the app open while it checks approval. If there is no pending request and the phone reports a timeout contacting `desktop-ip:8443`, the phone cannot reach the TLS listener. Confirm LAN access is enabled and active after restarting the desktop service, the newly generated QR contains the desktop's current Wi-Fi IP, both devices use the same Wi-Fi, and Windows Firewall permits the Python service on the Private network. The app now identifies which pairing step timed out and retries temporary timeouts while checking for approval.

The mobile client pins the desktop certificate fingerprint carried by the pairing QR. A device ID identifies this app installation; a separate device credential authorizes it. The credential and desktop details are stored by `flutter_secure_storage`. The audio foreground service and the new Flutter WebRTC/voice-message clients use the same certificate fingerprint and device token.

## Phase 3 audio session

Call protection asks for microphone, phone-state, and (on Android 13+) notification permissions only after the user chooses **Arm call protection**. Camera permission is used for QR scanning and is not required to arm call protection. If the required permissions are granted, Android displays **Armed · microphone off** while waiting. Android call-state monitoring starts microphone capture at `CALL_STATE_OFFHOOK` (which can include outgoing dialing, active, or held calls) and stops on idle, ringing, user stop, desktop connection loss, or capture failure. The phone sends mono PCM16 at 16 kHz in 20 ms frames to the paired desktop over authenticated WSS. No audio file is written on the phone. Capture behavior and whether speakerphone audio is available must be checked on the actual phone; ordinary apps are not guaranteed to get call audio.

The paired **Connected to desktop** indicator confirms the Phase 2 control channel only. Cellular Protection opens a separate authenticated WSS audio channel. Controlled phone-to-phone calls use the paired control channel for desktop-authorized call IDs and SDP/ICE relay, peer-to-peer WebRTC for the call, and separate authenticated WSS audio channels for Phone B's near/far VDA1 tracks. The desktop uses a local self-signed certificate, so the phone authenticates its exact SHA-256 certificate fingerprint saved during pairing; the LAN IP hostname may change independently when DHCP or network interfaces change. Re-pair if the certificate fingerprint changes. Restart the updated desktop service after updating its Python code, and rebuild/install the updated APK after changing the mobile client.

When the dashboard says **Receiving audio frames**, it confirms that correctly framed data is arriving. Check the signal meter and latest-frame diagnostic separately: a peak of `0` means all 320 PCM samples in that 20 ms frame were zero, so transport is working but microphone sound was not present in that sampled frame. The user verified that the diagnostic 440 Hz tone arrived and played audibly through **Play recent 5 seconds**, confirming the non-silent WebSocket-to-dashboard-playback path. Cellular-call microphone access is device/OS dependent; the live call tests so far have received frames whose sampled latest frames had zero RMS and peak, so usable microphone input during a cellular call remains unverified.

On 2026-10-08, a live speakerphone call delivered frames at roughly 50 frames/second with no sequence gaps or drops, but all five sampled latest frames had peak and RMS `0`. This device/run therefore confirmed WSS transport, not usable microphone input during the call. Keep the microphone-source result separate from transport status; consult the Phase 3 live observation in `docs/ROADMAP.md` before interpreting this behavior.

## Pairing and disconnect actions

- **Reject on desktop:** rejects the pending request before a device credential is issued. The phone shows that the desktop rejected the request; start a fresh pairing to try again.
- **Revoke on desktop:** invalidates the phone's credential on the desktop and closes its active connection. The dashboard marks the device **Revoked**. The phone reports that it is no longer paired; use **Forget this desktop and pair again** to clear its saved desktop details from the phone before pairing again.
- **Remove pairing from this phone:** clears the saved desktop address, certificate pin, and credential from this phone. It does not delete the desktop's device record; the dashboard shows that device as **Disconnected** and still offers **Revoke**. Revoke it on the dashboard as well if you want the desktop to invalidate that device credential.

These actions are intentionally separate: forgetting locally clears this phone's stored connection details, while revoking disables the credential at the desktop so it cannot reconnect.

## Network interruption and recovery

If Wi-Fi is interrupted while paired, the app shows **Disconnected / retrying** or **Connecting securely** and reports that the desktop is unavailable. It retries automatically with backoff. After the phone can reach the desktop again, it reauthenticates and returns to **Connected** without requiring a new QR pairing. The desktop dashboard shows **Disconnected** during the interruption and **Connected** after the session is restored. This recovery behavior has been confirmed during a live Wi-Fi interruption. If the desktop service is stopped, the phone becomes disconnected and continues trying to reach it; the browser dashboard becomes unavailable while the service is stopped. When the service is restarted, the existing pairing reconnects and both phone and dashboard return to **Connected**. This has also been confirmed live.

iOS uses the same Flutter UI conceptually, but this checkout does not yet include an iOS target. Platform call capabilities remain separate and do not imply general access to cellular-call audio.
